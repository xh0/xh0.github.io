High-Performance Network Applications with Rust

Chapter 39 — Network Services with Databases

A high-performance asynchronous Rust network server can easily accept 50,000 concurrent client connections. However, relational databases like PostgreSQL or MySQL cannot handle 50,000 active database connections simultaneously. Bridging the gap between high-concurrency async runtimes and database engines requires rigorous connection pool engineering.

The Connection Pool Paradox

A common antipattern among engineers new to async systems is setting the database connection pool size equal to the expected number of concurrent HTTP requests (e.g., setting max_connections = 5000).

In PostgreSQL, each connection is an independent operating system process. When 5,000 backend processes compete for 16 physical CPU cores, the kernel spends almost all its CPU cycles context-switching between processes and arbitrating disk I/O lock contention. Throughput collapses, and query latency spikes into seconds.

The Ideal Pool Size Formula

HikariCP and database performance engineering research establish a well-known empirical rule of thumb for optimal pool sizing:

$$\text{Pool Size} = (\text{Core Count} \times 2) + \text{Effective Spindle / SSD Count}$$

On a modern 16-core database server with an NVMe SSD array, the ideal pool size is often between 32 and 64 connections. A small pool of 50 connections running at zero queue contention will process far more transactions per second than a congested pool of 2,000 connections.

Connection Pooling with sqlx

Rust’s sqlx crate provides an asynchronous, pure-Rust connection pool with compile-time checked queries and built-in connection lifecycle management:

#![allow(unused)]
fn main() {
use sqlx::postgres::{PgPool, PgPoolOptions};
use std::time::Duration;

pub async fn configure_database_pool(database_url: &str) -> Result<PgPool, sqlx::Error> {
    PgPoolOptions::new()
        .max_connections(50)
        .min_connections(10)
        .acquire_timeout(Duration::from_millis(500))
        .idle_timeout(Duration::from_secs(300))
        .max_lifetime(Duration::from_secs(1800))
        .connect(database_url)
        .await
}
}

Critical Pool Configuration Parameters

  • acquire_timeout: The maximum time an HTTP request will wait in line to check out a database connection from the pool before failing fast. If the pool is exhausted, fail within 200–500ms and return 503 Service Unavailable rather than letting thousands of requests pile up in memory until the server crashes.
  • idle_timeout: Prunes connections that have sat idle, freeing up socket and memory resources on the database server.
  • max_lifetime: Periodically recycles connections to prevent memory fragmentation and cleanly handle cloud load-balancer connection terminations.

Query Pipelining and Prepared Statements

Prepared Statements

Parsing SQL strings, validating table schemas, and computing query execution plans is computationally expensive. Prepared statements compile the SQL query once and assign it a numeric handle. Subsequent executions simply pass the query parameters over the wire in binary format.

Query Pipelining

In traditional request-response database drivers, the client sends Query 1, waits for the response, and then sends Query 2.

In Query Pipelining, the client sends Query 1, Query 2, and Query 3 back-to-back without waiting for responses between them. The database executes them sequentially and streams the results back, amortizing network round-trip latency (RTT) across multiple operations.

Traditional (Non-Pipelined):
Client ──[ Query 1 ]──> Database
Client <──[ Result 1 ]── Database (1 RTT)
Client ──[ Query 2 ]──> Database
Client <──[ Result 2 ]── Database (2 RTT)

Pipelined:
Client ──[ Query 1 ][ Query 2 ][ Query 3 ]──> Database
Client <──[ Result 1 ][ Result 2 ][ Result 3 ] Database (1 RTT total!)

Exercises

  1. Beginner: Configure an sqlx connection pool connected to a local SQLite or PostgreSQL database and execute 100 concurrent queries using tokio::spawn.
  2. Intermediate: Simulate database pool exhaustion by creating a pool with max_connections(2) and spawning 20 concurrent requests that execute a 1-second query. Observe how acquire_timeout prevents unbounded queue growth.
  3. Advanced: Implement an asynchronous read/write splitting router in Rust that routes mutating SQL queries to a primary pool while distributing read-only SELECT queries across an array of read replica pools using round-robin selection.
